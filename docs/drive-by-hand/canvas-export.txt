    <text id="mqxd" v="2">SETTLED, by the second writer, 2026-09-22: yes - a Canvas-Next: may name a command that exits non-zero, and one word says which one it may not. A command written after the word `run` is the repair: it is printed ready to run against real paths, running it is what makes the refused command work, and it exits 0. Everything else a next action names is either a diagnostic - `ls -ld`, `ls -l`, `df -h`, `ulimit -n`, there to show the state that produced the refusal - whose exit status is the answer and not a failure; or a form, a command with a &lt;placeholder&gt; in it that nobody runs as printed. So the rule the tool holds itself to is not 'every command a next action names succeeds' but 'every command a next action tells you to run succeeds'. The reason is not taste, it is what happened when I ran it. Option A - every command must exit 0 - is not implementable without gutting the surface: rendering all fifteen templates against a path that is genuinely gone and running every backticked command in each shows that four of them are not commands at all (`ulimit -n` is a shell builtin, `| cat | head -1` and `| head -1` are pipe fragments, `chown` is named bare with no operands) and that the ENOENT template's own repair exits 2 run verbatim, because it prints &lt;ledger-id&gt; where a ledger id goes. The remaining diagnostics exit 1 on precisely the condition their template exists for, because every way of looking at a path that is gone reports that it is gone by exiting non-zero. A would therefore either forbid a refusal about a missing path from telling a caller to look at it - the one thing a caller facing ENOENT most needs - or leave assertRepairsRun holding the hand-maintained allowlist that condition (3) was written to remove. B costs one marker, and the marker is syntactic rather than a list of command names, so a template that adds a repair nobody anticipated is covered the moment it is written.</text>
